# E3 端到端延迟分解报告

口径：无头回放（logs/ 真实弹幕，3× 加速注入，间隔封顶 6s），真实 DeepSeek 评分+回复、真实 DashScope CosyVoice 流式合成，播放替换为写 WAV（play_start=开始出声，voice_end_est=出声结束推算值）。
LLM 调用为非流式（ai_chat.py 无 stream），故只有 LLM 完成点，无首 token 点；TTS 首包延迟取 DashScope get_first_package_delay()。

**负载定性（红审修订）**：本轮注入 λ≈10 条/分钟 > μ≈7 条/分钟（实测服务率），属于**过载压力测试**，排队延迟是队列增长的必然结果，不是稳态延迟。观众体验的稳态口径见 λ=3 档负载扫描（e3_load_report.md）。

**n 差异说明**：评分段及含评分的①行 n=75（仅弹幕），3 条礼物本地赋分零延迟（t_scored=t_arrive）不计入；占坑 commit 条目评分照常有 score_start/scored 段，不影响 n。本系统到达即评分，排队发生在评分完成之后，故①管线处理=评分+LLM+TTS 三段实耗之和。

## API 调用与成本粗估

- pipeline: 评分 75 次（deepseek-v4-flash），回复 78 次，TTS 78 次 / 约 3151 字符
- serial: 评分 75 次（deepseek-v4-flash），回复 65 次，TTS 64 次 / 约 2710 字符

两臂合计：DeepSeek ~300 次调用（评分 ~140 + 回复 ~142，含少量重试），token 量级约 10^5，费用 < ¥2；CosyVoice TTS 约 7000 字符，费用 < ¥1。总计远低于预算红线。

## 口径与局限

- 弹幕到达时刻 = 回放器注入时刻（等价 danmaku_bot 收到事件）；礼物本地赋分零延迟，t_scored = t_arrive。
- ai_chat.py 为非流式调用，无 LLM 首 token 点位；若改流式可补上。
- TTS 首包延迟由 DashScope SDK 的 get_first_package_delay() 给出（约 800ms），完整合成 2.5s 左右；流式播放场景下感知延迟更接近首包口径。
- 无头模式 play_start 即"开始出声"，出声结束 = play_start + 音频时长（推算）。
- 排队+停顿段含 scheduler 的 0.5-1.5s 随机句间停顿与级联等待（Q1空8s/Q2空20s）。
